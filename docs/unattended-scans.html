Part one is written for anyone. From “Five steps” onward it assumes a terminal.

Scheduled accessibility runs

Same checks, nobody watching

The scanner runs on a timer, compares each run with the last, and speaks up only when something broke.

What this is

The app in your browser lets you build a workflow: go to this page, log in, open that menu, check for accessibility problems. You press Run, and it tells you what it found.

This does the same thing without anyone pressing Run. A computer can start it at three in the morning, every night, and tell you what changed since last time.

Why the comparison is the point

A single scan answers “how is this page today?”. That is useful once. What teams actually need is the other question: did we just make it worse? Nobody answers that from one report, because it means remembering what last week looked like — and reports pile up unread.

Yesterday this page had 11 problems. Today it has 11 problems.

But four of yesterday’s were fixed, and four new ones appeared.

The total never moved. Something still broke. Only a comparison sees that.

What lands on disk, every run

FileWhat it isWho reads it
summary.mdThe run written out in prosePeople
diff.jsonExactly what changed since the compared runOther software
comparison.htmlThe same comparison as a page, as the app’s Compare tab downloads itPeople
payload.jsonThe complete result, same as the app producesThe app, later comparisons
run.log.jsonlLine by line, what the workflow didWhoever is debugging

diff.json and payload.json are described by schemas/diff.v1.schema.json and schemas/report.v2.schema.json, for whatever reads them. Every failing element has an occurrenceId that stays the same from run to run, so a ticket filed for one can be found again in the next run’s files.

summary.md is the one to read:

# Regression demo

**New failing instances since the baseline**

- Url: https://example.com/checkout
- Run: run_744e9f59 at 2026-08-17T17:03:51.613Z

## This run

- Scans: 1
- Failing: 4 rules, 4 instances
- Can't tell: 1 rules, 1 instance

## Compared to release-1.0

- Rules: 3 new, 1 resolved, 1 persistent
- Instances: 4 new, 9 fixed, 0 still failing

### New

- **button-name** (critical) — 1 instance
- **color-contrast** (serious) — 1 instance
- **link-name** (serious) — 1 instance

Three words that appear everywhere

Rule
One kind of problem. “Buttons must have a name” is a rule.
Instance
One place that problem actually occurs. One rule can break in eight places.
Baseline
The earlier run being compared against — the last one, or one you deliberately kept.

What it can honestly claim

Worth reading even if you skip everything else.

It can tell you

That a specific, machine-checkable problem appeared where there wasn’t one before. That is a real signal, and it is worth acting on.

It cannot tell you

That a page is accessible. Automated checking finds a fraction of real problems, and none at all of the kind needing human judgement: is this alt text actually describing the picture? Does the page make sense read aloud, in order? Can someone finish the task?

That is why the score is labelled an automated result rather than a grade, and why the runner refuses to pass or fail your build on a score. It fails on one thing: a problem that wasn’t there before. That is a claim it can stand behind.

It also says when it didn’t do its job

If the workflow was meant to click through to page seven and the button was missing, the scan never happened. A scan that never happened reports zero problems — which looks like excellent news.

The runner catches that and calls the run degraded, because “fewer problems than yesterday” means nothing when half the run didn’t happen. For unattended runs this is the single most valuable thing it does.

A real example from testing: a scan was skipped because the page was too large. The run found zero failures, and the comparison read 9 fixed, 0 new — everything apparently repaired overnight.

It exited 4 degraded instead of 0 clean.

Five steps to a nightly run

Step 1

Build the workflow in the app, then export it

You don’t write workflows by hand. Build it where you can watch it work, then press Export config and save the file. That file has everything the runner needs, and it loads back into the app later.

A password is never saved in that file. For a run nobody watches, have the Set password value step read it from the environment instead: "value": { "$env": "SHOP_PASSWORD" }. The runner reads the variable as the run starts, gives it to the browser only, and stops before opening one, with exit 2, when it is not set.

Step 2

Run it

terminal
node src/cli/run-workflow.js checkout.json

Status      done
Scenario    Checkout
Url         https://example.com/checkout
Run id      run_ddeea58f7a86868c
Steps       12 of 12
  by type   a11yScan 4, click 4, screenshot 2, navigate 1, forEachElement 1
Scans       1
Failing     2 rules, 9 instances
Can't tell  1 rules, 1 instances
Diagnostics 1 console, 0 request failures, 1 bad responses
Payload     a11y-runs/Checkout/runs/2026-08-17T10-00-00-000Z/payload.json (1833 KB)

Steps is how much of the workflow actually ran. On a run that stopped early it reads 5 of 12 (7 not run): worth checking before reading the findings, since half a workflow finds half the problems. A forEachElement with no limit, or a crawlQueue with no maxPages, only learns its size as it runs, so the total carries a tilde until it does: 5 of ~12 (2 loops never sized).

Add --quiet for the summary without the running commentary.

Step 3

Run it again tomorrow, and compare

terminal
node src/cli/run-workflow.js checkout.json --baseline auto

Compared to 2026-08-17T10-00-00-000Z
Rules       3 new, 1 resolved, 1 persistent
Instances   4 new, 9 fixed, 0 still failing
  new       button-name (critical) 1 instance
  new       color-contrast (serious) 1 instance
  new       link-name (serious) 1 instance

auto means “the previous run of this scenario”. The first time, there is nothing to compare with — it says so plainly and does not treat that as a failure, unless --fail-on-failures asks it to fail a first run that has failures. When something does break, the command finishes with exit code 3, which is how a build system learns without reading anything.

Step 4

Keep a baseline that doesn’t move

“Since last night” is one question. “Since we released” is another, and auto can’t answer it, because last night’s run already contains the problem you shipped a week ago.

terminal
# on release day
node src/cli/run-workflow.js checkout.json --promote release-1.0

# from then on
node src/cli/run-workflow.js checkout.json --baseline @release-1.0

A run that failed, was cancelled, or came back degraded cannot become a baseline. If a broken run became the reference, every run after it would look like an improvement — forever.

Step 5

Put it on a schedule

Nothing left to build. A nightly run keeping a fortnight of history:

crontab
0 3 * * * cd /path/to/a11y-testing && \
  node src/cli/run-workflow.js specs/checkout.json --baseline auto --keep 14 --quiet

In a pipeline, the exit code does the work: 0 carry on, 3 something broke, 4 the run didn’t cover everything so its result can’t be trusted.

To tell a person, mail or post the summary.md the run just wrote. The runner writes the file and stops there — every team’s mail, chat and ticketing is different.

Options

--url is how one workflow serves several environments — the same steps against staging or production.

Exit codes

CodeMeaningWhat to do
0Ran, nothing newNothing
1The run failedRead summary.md and run.log.jsonl
2Bad options, or an unusable spec (with --check: it has errors)Fix the command or the file
3New failing instances against the baseline; with --fail-on-failures and no baseline, any failing instanceLook at what appeared
4Covered less than the spec asked forFix the workflow, then re-run
5With --fail-on-lean: new likely failures, no new failureConfirm them by hand
130Cancelled with Ctrl+CNothing; the partial result was still written

Codes 1, 130 and 4 outrank 3, in that order, and 3 outranks 5. A run that didn’t finish, or didn’t cover what it should, makes the comparison unsound rather than merely worse — so it is reported as its own problem rather than as a regression.

Where files go

--keep only ever deletes folders inside runs/ that contain a payload.json. Promoted baselines live outside runs/ and are never pruned.

payload.json names its screenshots by their path in images/ (images/<hash>.jpg), as a report package does, so the run’s folder is one: zip payload.json with images/ and the app’s open report and compare tabs load it with its pictures. Loaded alone, payload.json shows its findings and says each picture is missing.

The spec file

A config exported from the app already contains everything below. This is the whole format, if you would rather write one by hand. The app opens a spec too, with Load config, to review it or change it in the builder before it runs: its vars go into a Batch row, and what the app has no setting for (a viewport size that is not a preset) is reported when it opens.

{
  "type": "a11y-run-spec",
  "specVersion": 1,

  "url": "https://example.com/checkout",
  "scenarioName": "Checkout",

  "actions": [
    { "type": "a11yScan", "label": "Cart", "profile": "en301549-v4.1.1", "context": "main", "exclude": ".ads, .cookie-banner" },
    { "type": "click", "selector": "#to-payment" },
    { "type": "a11yScan", "label": "Payment", "context": "main" }
  ],

  "viewport": "desktop-lg",
  "customSteps": []
}

scenarioNamenoNames the folder and the reports

A run has no Include or Exclude selectors: each scan step’s own context and exclude say what it checks. A spec saved with them for the whole run stops with an error naming them: node src/cli/convert-config.js <file> --write puts them on its scans, as the run applied them.

A run has no profile either: each scan step’s profile sets what it checks against, wcag22-a, wcag22-aa or wcag22-aaa, or a standard, en301549-v4.1.1 or en301549-v3.2.1; without one, wcag22-aa.

Checking a spec before it runs

--check reads the file and stops there, without opening a browser:

node src/cli/run-workflow.js specs/checkout.json --check

It checks the fields above, and every step, nested ones and custom steps included, against schemas/run-spec.v1.schema.json. That schema is generated from the same action definitions the app’s builder uses, so it knows every step and every field. It sorts what it finds into two kinds:

  • Errors stop the check with exit 2: a missing required field, a step type the engine does not have, a value of the wrong kind, such as the text "true" where a field takes true or false (the engine would read it as if it were absent), a runCustomStep naming a custom step the spec does not have, a scan whose engine cannot check its profile.
  • Warnings leave it at exit 0: a field the step does not declare, or a value outside the ones the app offers. The run goes on, but they are usually typos.

Every run makes the same checks before it starts, whether it starts from the app, the queue or the command line: a workflow with errors does not start, each error in its log (from the command line, exit 2), and the warnings go to its log as it runs.

Add "$schema": "./schemas/run-spec.v1.schema.json" (the path from your spec to the repository’s schemas/ folder) at the top of a spec, and an editor that reads JSON Schema completes step types and fields as you type and marks mistakes as you make them.

Trying a workflow without scanning

A site changes, and a workflow written against it last month may no longer fit: a button renamed, a menu moved. --dry-run finds out in seconds, without the scans:

node src/cli/run-workflow.js specs/checkout.json --dry-run

It takes every step in a browser, as a run would, except the scans, screenshots and evidence, then says how each step went:

Dry run    https://example.com/checkout
  done     1    Click "Accept cookies"
  done     2    A11y scan "Cart"
                would check nothing: its context "#basket" matches nothing on the page
  FAILED   3    Checkout (at step 3.1): click failed: "#checkout" not found
  not run  4    A11y scan "Payment"
Scans      2 scans not run, 1 of them would check nothing (said under its step)
Result     the workflow does not fit the site as it stands: 2 problems above

A step that failed inside another says where (3.1 is the first step in step 3). A scan is not run, but its context selector is looked for, since a scan whose context matches nothing would report a page with no problems. Nothing is written, so a dry run never becomes the run --baseline auto compares with. Exit 0 when every step ran, 4 when one did not.

The app has the same check: Dry run, next to Run, shows the same list under the buttons and leaves the last report as it was. With the batch on, it uses the batch’s first workflow.

Running a batch

The app’s Batch section runs one workflow once per row: each row its own name, its own starting page and its own variables. The runner does the same, from a batch spec:

{
  "type": "a11y-batch-spec",
  "specVersion": 1,
  "name": "Product pages",
  "spec": { "type": "a11y-run-spec", "specVersion": 1, "url": "https://example.com/",
            "actions": [{ "type": "a11yScan", "label": "{var:product}" }] },
  "rows": [
    { "name": "Shoes", "url": "https://example.com/shoes", "vars": { "product": "Shoes" } },
    { "name": "Bags",  "url": "https://example.com/bags",  "vars": { "product": "Bags" } }
  ]
}

or from a configuration saved in the app with its batch on, which runs as a batch there too (--no-batch runs its workflow once instead). The rows are read by the same code as the app’s, so a row the app would refuse is refused here with the same words, and --check checks the workflow and every row. schemas/batch-spec.v1.schema.json describes the file.

node src/cli/run-workflow.js specs/products.batch.json --baseline auto --keep 14

Each row runs in turn, in its own folder (a11y-runs/Product-pages/batches/<stamp>/01-Shoes/), with its own payload.json, summary.md and, when compared, diff.json; batch.json beside them lists every run with its status, counts and exit code, in the queue’s own format. --baseline auto compares each row with its run in the previous batch; @name with the baseline promoted for that row, which --promote name keeps for every row that ran whole. --keep counts batches. --dry-run tries the first row’s workflow, as the app’s Dry run does. The batch exits as its worst run: cancelled, then failed, degraded, new failures, new likely failures.

When something goes wrong

Spec must have a url
Exit 2 — the file isn’t a usable workflow. Export it again from the app.
“tags” is not read any more, programmatic must be true or false, “AA” is not a profile
Exit 2 — the file was saved in an older format. node src/cli/convert-config.js <file or folder> says what it would change, and with --write brings the files up to date; opening and saving each one in the app does the same.
Unsupported protocol: file:
Only http and https are allowed. Serve the page over HTTP, even locally.
no previous run to compare with yet
Not an error. --baseline auto on a scenario that has never run has nothing to compare with. The next run will. To fail such a run when it has failures, add --fail-on-failures.
the baseline is newer than this run
You compared against a run that happened later. It still works, but “new” and “fixed” are the other way round from what you probably meant.
1 scan skipped
Exit 4 — a page was too large for the scan’s node threshold, so it was never scanned. It reports zero problems for that page, which is why this is a failure and not a pass.
12 iterations failed
Exit 4 — a loop over elements broke partway. Usually the page changed shape mid-run, or a selector matches something that disappears. Fix the workflow before trusting the numbers.
not promoting a degraded run to a baseline
Working as intended. Fix the run, then promote it.
The numbers differ from the app
Check what the scans check against and how the page is shown: each scan’s profile, and the spec’s viewport, colorScheme and language, against the app’s run.

Words used here

Accessibility scan
An automated check of a page against a set of rules.
Rule
One kind of problem, such as “images need alternative text”.
Instance
One place a rule is broken. Eight images without alt text is one rule, eight instances.
WCAG
The international accessibility standard. Levels A, AA and AAA run from basic to most demanding; AA is the common legal target. Versions 2.0, 2.1 and 2.2 build on each other.
Can’t tell
The checker found something it can’t decide alone. Not a pass, not a failure — a place a person needs to look.
Workflow
The sequence of steps: go here, click that, scan now.
Spec
The file describing a workflow so it can run without the app.
Scenario
A name for one workflow, used to group its runs.
Baseline
The earlier run a new one is compared against.
Regression
A problem present now that was not in the baseline.
Degraded run
A run that finished but did less than asked: a scan skipped, a loop that lost iterations, an action that failed. Its numbers aren’t comparable with a whole run’s.
Payload
The complete machine-readable result of one run.
Exit code
The number a command leaves behind so other software knows how it went. Zero means fine.

For maintainers

The runner is a thin layer over the same code the app uses. Nothing about scanning is duplicated for it.

PieceWhereWhat it does
Entry pointsrc/cli/run-workflow.jsArguments, output files, exit code
Spec handlingsrc/shared/run-spec.jsReads and validates a spec or exported config
Run storesrc/cli/run-store.jsFolders, auto and named baselines, pruning
Comparisonsrc/shared/report-diff.jsThe same diff engine as the app’s compare tab
Coverage checksrc/shared/run-health.jsDecides whether a run was whole
Prosesrc/cli/summary-report.jsWrites summary.md
The run itselfsrc/server-side/workflow-run.jsShared with the server’s /workflow-start route

Two rules hold this together, and both are tested rather than trusted:

  • The app and the runner build their run request with the same function, so a saved workflow and a scheduled one cannot mean different things.
  • src/shared/tier-boundaries.test.js fails if browser code and Node code start importing each other, or if the viewport presets stop agreeing across the page, the action definition and the engine.

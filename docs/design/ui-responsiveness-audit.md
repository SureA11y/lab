# UI responsiveness audit: large reports

This audit measures how the lab's interface *feels* with a large report. It
does not measure how long scans or server work take. Two things are measured:
how fast each click gets a visible reaction, and how long the page stays
frozen afterwards. It changes no code. It is the baseline that any future
change should be measured against.

## Test setup

**Report.** A real report produced by the CLI runner (`spec-big.json` run
against a page generated by `gen-page.js`, which is full of failures):

| | |
|---|---|
| Scans | 24 (12 full page, 12 sections) |
| Findings | 1,020 (8 failing rules, 4 can't-tell rules) |
| Occurrences (flagged elements) | 29,412 |
| Element screenshots | 29,304 (served as files) |
| `payload.json` | 84 MB |

A second report was used to separate image cost from DOM cost: the same run
with Element screenshots off (79 MB).

**How it was measured.** Playwright drove headless Chromium against the local
server, on a 4-core Xeon at 2.8 GHz with a 1440×900 viewport. Each
interaction records:

- **First feedback**: Event Timing duration, from the click to the next paint.
  This is when the user sees *anything* change.
- **Longest freeze**: the longest single main-thread task. The page cannot
  respond, animate or repaint during it.
- **Until done**: until the result is on screen.

The numbers varied by about ±30% between runs. A fast desktop will be quicker
in absolute terms, but the ranking holds. Targets used: first feedback
≤ 100 ms, no freeze over ~200 ms, and anything longer than ~1 s shows
progress.

To reproduce, use the scripts in [`ui-responsiveness-audit/`](ui-responsiveness-audit/):

1. `node gen-page.js fixture.html`, then serve it on
   `http://127.0.0.1:8099/`, for example with
   `python3 -m http.server 8099 --bind 127.0.0.1`.
2. Build the report:
   `node src/cli/run-workflow.js docs/design/ui-responsiveness-audit/spec-big.json --out <dir>`.
3. Start the lab with `npm start`, then run:
   - `node audit.js <dir>/payload.json big`, for the timings;
   - `node profile.js <dir>/payload.json`, for the CPU breakdown and DOM
     counts.
4. For the queue scenario, queue a few copies of the spec, then run
   `audit.js … --queue` and `queue.js`.

The scripts need Playwright. Set `PLAYWRIGHT_MODULE` if it is not installed
in the project.

### Without element screenshots (79 MB)

Every number improves by only 10–25%: Load 2.9 s freeze, tab switch back
2.4 s, grouping 2.1 s. The exception is the **ZIP export, which drops from
~100 s to 15.5 s**. Element screenshots drive the export time, but not the
freezes. The freezes come from the size of the DOM (see below).

### With a batch running in the queue (4 large workflows, 2 at a time)

| Interaction | Longest freeze | Until done |
|---|---:|---:|
| Switch back to open report (from run workflow) | **2.8–3.7 s** | 3.3–4.3 s |
| Load selected | **5.2 s** | 5.4 s |
| Scroll through results | worst frame 133 ms | 14 of 60 frames slow |
| Open report → queue → open report | 0.12 s (cached) | 0.8 s |
| Queue polling, queue tab visible, 20 s window | 0 long tasks | — |

A running batch adds about 20–30% to the freezes, because the server's
Chromium instances compete for the same CPU. In a real setup that CPU
competition is the user's own machine. **The queue panel's own polling and
re-rendering is not a measurable cost.** One reading showed 2.9 s blocked in
20 s, but that was the tail of a ZIP export that had just finished, not
polling.

## Where the time goes

### 1. 98% of the DOM is hidden "View details" dialogs

Measured after loading the big report:

| | |
|---|---:|
| Elements in the document | **726,623** |
| Elements inside the 276 `<dialog>`s in `#results` | **709,924** (97.7%) |
| Serialized page HTML | 68 MB |
| `<img>` elements | 3,769 |

Every issue row builds its "View details" dialog in advance, with every
occurrence's markup and screenshot placeholder in it
(`buildInstancesCellHtmlForIssue`, `src/js/a11y-ui.rendering.js:721`;
`buildInstancesListHtml`, `:604`). Most users open very few of these dialogs,
but every render pays for all of them:

- **Building them** is the biggest single cost in the CPU profile. `renderTable`
  (`a11y-ui.rendering.js:1106`) parses the HTML string via `innerHTML` and
  takes ~1.0 s per render. Add DOM insertion (`appendChild` ~0.4 s) and the
  engine's own style and layout work ("program", 0.6–1.1 s).
- **Throwing them away** costs again on every tab switch and grouping change
  (`removeChild`, GC 0.1–0.3 s).
- **Everything else slows down** with them. `showModal()` on one dialog takes
  300–400 ms, and changing the presentation mode means a style recalculation
  over the whole document.

The run without element screenshots still has 640,000 elements, so the
dialogs' *markup*, not the images, is the problem.

### 2. Run and open report share one results area, so switching tabs rebuilds it

The run and report buckets render into the same `#results`. `setActiveMode`
(`src/js/a11y-ui.js:303`) skips the redraw only when the area already shows
the same tab's payload (`resultsRenderedFor`, `:331`). That case only arises
after a round trip through Compare or Queue: open report → queue → open report
took 0.12 s in the measurements. Every switch between **run workflow** and
**open report** tears the whole report down and rebuilds it from scratch. That
is the multi-second reaction described in the original question.

### 3. The tab doesn't even look selected until the rebuild finishes

`setActive` (`src/js/tabs-ui.js:24`) dispatches `a11ylab:modechange` first, and
its listener renders synchronously. Only afterwards does `setActive` set
`aria-selected` and show the new pane. So during the 2.6–3.7 s freeze, the
user sees the *old* tab still selected and nothing happening. This matches
the 2.9 s first-feedback figure, and it is why the click feels ignored rather
than just slow.

### 4. Every heavy action is one long synchronous task

There is no Web Worker, no chunking, no yielding between stages, and no
lazy or virtualized rendering. `renderFinalPayload` (`a11y-ui.js:8888`) and
`finalizeAndRenderAll` (`:8611`) build the summary, the global table, the
dispersion section, every scan card and every dialog in one go. Even when a
spinner has been painted first (`runBusy` / `afterPaint` in `src/js/busy.js`,
used by Load selected and the queue's Open), it then sits frozen for 3–5 s.

### 5. Some controls give no feedback at all

These start a full rebuild with no busy state, so the select or button just
appears stuck:

- the grouping select (`applySelectedBuiltInGrouping`, `a11y-ui.js:1953`);
- the engine filter (`onEngineFilterChanged`, `:8393`);
- the include/exclude toggles (`toggleScanIncludedInReport`, `:372` →
  `refreshDerivedReportUi`, `:7713`).

"Include again" is worse than "exclude" (3.0 s vs 1.3 s blocked) because it
runs as two long tasks back to back.

### 6. Smaller costs on the load path

- The staged file is parsed twice and validated twice: once when staging, and
  again in `freshReportObject` (`a11y-ui.js:2519`, ~0.23 s for 84 MB).
- `dedupeWithUrlMerge` (`a11y-ui.rendering.js:423`) takes ~0.15 s per render.
- Thumbnail and image work (`buildThumbFrame`, `imgToBtn`, `createImg`) takes
  ~0.2 s per render.

Each of these is small compared with points 1–4.

### 7. Export is slow but not frozen

The ZIP export keeps the page responsive: its longest task is ~0.2 s. But it
takes ~1.5 minutes with element screenshots, shows no progress, and pushes the
JS heap from ~150 MB to ~650 MB, because it clones the 726,000-element DOM
and gathers the images. Without element screenshots it takes 15 s.

## Ranked: where the experience hurts most

Ranking weighs how often the user does it against how bad it feels.

1. **Switching between run workflow and open report.** It happens constantly,
   the page freezes for 3–4 s, and the tab doesn't visibly react. (Points 2, 3, 1.)
2. **Opening a report**, via Load selected or the queue's Open. The page
   freezes for 3–5 s with the spinner frozen. (Points 1, 4.)
3. **Grouping and engine filter changes**: a 2–3 s freeze with no feedback.
   (Points 1, 5.)
4. **Include/exclude a scan**: 1.3–3 s with no feedback. (Point 5.)
5. **View details**: 0.3–0.4 s before the dialog shows, and it gets worse as
   reports grow. (Point 1.)
6. **ZIP export**: up to 1.5 min with no progress indication. (Point 7.)
7. Presentation mode, scrolling, and the run workflow and queue tabs:
   acceptable today, but they scale with DOM size, so they will degrade
   alongside the items above.

## Directions this pointed to

These were the directions the measurements suggested. All of them except the
Web Worker were then implemented; see **After the changes** below.

- **Build "View details" content on first open.** Keep only the trigger in
  the table and render the dialog body from the data when it is opened. This
  removes ~98% of the DOM, and with it most of the cost of items 1–5.
- **Give each tab its own results area and hide the inactive one** instead of
  clearing it. Switching tabs becomes a visibility change. Combined with the
  previous point, the memory cost of keeping both areas is small.
- **Mark the tab selected and show the pane before rendering.** Swap the order
  in `setActive`, or yield a frame before the render, so the click reacts
  within one frame even before anything else changes.
- **Render in stages and yield between them:** summary first, then scan cards
  (as they scroll into view, or in small batches), then secondary sections.
  The page stays interactive, and the most useful part appears first.
- **Use `content-visibility: auto` on scan cards and large sections**, so
  off-screen content skips layout and paint.
- **Busy feedback on the grouping select, engine filter and include toggles**,
  using the existing `runBusy` helper.
- **Progress for ZIP export** (stage and count), and parse the staged file
  once.
- Later, if the first steps aren't enough: move parsing and data preparation
  to a Web Worker.

## After the changes

**Changes made**, one commit each:

1. A tab is shown as selected before its results are drawn.
2. The grouping, engine and include/exclude controls show that they are
   working before they redraw.
3. `content-visibility: auto` on scan cards was already in place.
4. "View details" occurrences are drawn on first open, behind a skeleton for
   long lists. The export draws them all.
5. Each tab's results are set aside and put back on a switch, not redrawn.
6. The scans of a long report are drawn four at a time.
7. The copy that Load selected uses is parsed in idle time. The export is
   faster and names its current step.

**How this was measured.** The same 24-scan report (`spec-big.json`, with its
element screenshots on the server) was measured before and after these changes, side by side on one
machine:
`BASE=… node audit.js` and `node export-freezes.js`.

**Later.** A report picked on its own now opens at once, without Load
selected, so the scripts time picking it until it is on screen (`audit.js`:
"pick file → report on screen", then Load selected pressed again). Run
twice on the code before and after `a11y-ui.js` was split into modules (30
October 2026), the report was on screen in about 1.05 s with a 0.32 s
longest freeze, tab switches had no freeze, a grouping change 0.08 s, and
scrolling no slow frame: the same, within noise.

|---|---|---|
| Elements on the page | 726,623 | **19,183** |
| Load selected → report on screen | 16 ms / **3.5 s** / 3.8 s | 16 ms / **0.5 s** / 0.6 s |
| Switch back to open report | **3.4 s** / 3.1 s / 3.6 s | **72 ms** / **none** / 0.13 s |
| Switch to run workflow | 128 ms / 0.1 s / 0.95 s | 40 ms / none / 0.06 s |
| Change grouping | none shown / **3.0 s** / 3.9 s | at once ("Updating the results…") / 0.4 s / 0.8 s |
| Exclude a scan | **1.3 s** / 1.1 s / 1.3 s | **40 ms** / 0.2 s / 0.3 s |
| Include it again | **1.4 s** / 1.7 s / 3.1 s | **40 ms** / 0.2 s / 0.5 s |
| Open View details | 370 ms / 0.24 s / 0.29 s | 120 ms / 0.19 s / 0.3 s |
| Presentation mode | — / 0.17 s / 0.7 s | — / none / 0.02 s |
| Scroll through the results | 15 of 67 frames slow | 0 of 50 frames slow |
| Download report (ZIP) | 32 ms / **2.4 s** / **114 s** | 24 ms / **1.4 s** / **13 s**, with its step shown |

The exported ZIP is unchanged. For both test reports, the HTML and every file
in the ZIP are identical to the original's. The only exception is the
narrative wording, which is seeded from the page's address and so differs
between servers on different ports.

**Trade-off.** Picking a file now costs a 0.3 s freeze, about a second after
the staged list appears, while the copy for Load selected is parsed. It saves
the same time when Load selected is pressed.

**Not done.** A Web Worker for parsing and data preparation. With the numbers
above it no longer looks necessary. The largest remaining freezes are the
0.5 s first draw of a report and up to 1.4 s inside an export.

**Measuring error worth knowing about.** Element screenshots are files under
`reports/`. A report whose files have been deleted still exports, but much
faster, because no pictures are fetched. So check that its files exist before
timing an export.

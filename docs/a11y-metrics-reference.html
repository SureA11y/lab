A11y Summary Metrics Reference

This document explains every index, value, and estimation produced by your metrics pipeline (DOM heuristics, text heuristics, signals derived from the scan's findings, and the final accessibility risk indicator), including the exact formulas and rounding rules needed to reproduce the same outputs.

Plain-language overview

What this report is

This output is a compact “health snapshot” of a page, based on three families of signals: (1) what surea11y can automatically detect, (2) how complex the page looks structurally, and (3) basic patterns about text and controls. It is designed for dashboards and triage, not for legal or formal conformance claims.

The goal is practical: if you only have the raw scan data, you can compute the same numbers and interpret them consistently across many pages.

What it is not

  • It is not a WCAG pass or fail verdict.
  • It is not “how accessible the page is” as experienced by users.
  • It does not replace manual validation, keyboard testing, screen reader testing, and design review.

The headline numbers, explained like a human

NumberMeaningHow to use it
scores.avgPageAccessibility “Automated check result.” For a single page, this is identical to scores.adjusted below. For a portfolio/global summary across multiple pages, it's the mean of the scanned pages' own scores. This is the one headline number that's always present, on both single-page and portfolio reports.
scores.evidence “How clean the page looks to automated checks.” Built from the findings' breadth and depth, normalized against how much of the page there was to check (evaluable elements, or a fallback unit when there were none) rather than raw DOM size. Use it as a quick signal. Low evidence usually means findings are widespread, or many different rules failed. High evidence means little was found, but it can still miss issues.
scores.confidence “How much you should trust the automated evidence.” The mean of the confidence surea11y reported on its fail/cantTell findings - a finding may carry none, so this can be null (“not measured”) rather than a guess. Read it as “automation reliability”, when it is present. A confidence of 85 means “use the evidence score, but keep some caution”. When it is null, treat evidence as unverified rather than assuming it is trustworthy.
scores.adjusted “Evidence, discounted when automation is less reliable.” This is your conservative dashboard score. Prefer this for a single KPI. It prevents pages that look clean but are hard to evaluate from being over-rated.

How to read “per 1k” values

Many metrics are normalized “per 1000 elements” so you can compare pages of different sizes. Without normalization, bigger pages always look worse, even if they are proportionally similar.

Example

Page A has 1000 elements and 100 links, that is 100 links per 1k. Page B has 10,000 elements and 100 links, that is 10 links per 1k. The raw count is the same, but the page structure is very different.

Why there are many metrics

A single score is easy to communicate but can be misleading. The supporting metrics exist so you can answer, “why is the score what it is” and “what should we do next”.

  • Breadth tells you whether problems are diverse (many rule types) or narrow (few rule types).
  • Depth tells you whether problems are widespread across many elements.
  • Structure signals tell you whether automation is likely to miss state, visibility, and component behavior.

Examples that make the math understandable

Breadth versus depth

Idea

Breadth is “how many different kinds of problems”. Depth is “how widespread the problems are”.

Example A, many kinds, not widespread

Imagine the scan finds 5 different rules failing, each on 1 element. That is high breadth (many rule types), but low depth (not many affected elements).

Example B, one kind, very widespread

Imagine the scan finds 1 rule failing, but it matches 400 elements. That is low breadth (one rule type), but high depth (widespread impact). This is often a systemic issue.

Why depth uses square root

If depth were linear, 400 matches would count 400 times worse than 1 match, which can drown out everything else. Using sqrt(n) still increases with n, but more gently: 

n = 1     => sqrt(n) = 1
n = 25    => sqrt(n) = 5
n = 100   => sqrt(n) = 10
n = 400   => sqrt(n) = 20

So 400 matches is treated as “much worse” than 1 match, but not 400 times worse.

Saturating score, what it does

A saturating score converts “bigger is worse” raw values into a 0–100 scale where the first problems hurt the most, and additional problems still hurt but with diminishing impact. This keeps the score stable and comparable.

Intuition

Going from 0 to some findings is a big signal. Going from 500 to 600 findings is not 20% more concerning in a useful way, it is already clearly problematic.

Interval bands, how the UI labels work

Many metrics include intervals like “good, warn, bad”. These are not absolute truths, they are thresholds chosen to classify values consistently. The logic checks whether a metric falls inside a band range. 

// Example: hiddenRatio band check
hiddenRatio = 0.32
interval warn: from 0.25 to 0.50
0.32 is inside, so hiddenRatio is “warn”

Confidence example, action by action

Suppose a page has 4 fail/cantTell findings. Only some of them carried a per-finding confidence - say a run mixing an engine that reports one with an engine that doesn't. 

// 4 verdicts (fail/cantTell), 3 of them carried a confidence
withConfidence = [0.90, 0.80, 0.70]

confidence         = mean(0.90, 0.80, 0.70) = 0.80  =>  scores.confidence = 80
confidenceCoverage  = 3 / 4 = 0.75                   =>  scores.confidenceCoverage = 75
confidenceSource    = 'partial'  (some, not all, verdicts carried one)

// Uncertainty is only spent over the 75% of evidence it was measured on:
effectiveConfidence = 1 - (1 - 0.80) * 0.75 = 1 - 0.15 = 0.85

// If evidence was 90 (riskContent = 10), adjusted spends headroom rather than multiplying:
uncertainty = 1 - 0.85 = 0.15
inflated    = 10 + 0.15 * 10 * ((100 - 10) / 100) = 10 + 1.35 = 11.35
adjusted    = 100 - 11.35 = 88.65  =>  rounds to 89

Rounding example

The output intentionally rounds many values to reduce noise between runs and between small DOM changes. 

riskContent = 13.766 => scores.evidence = round(100 - 13.766) = 86
confidence  = 0.80   => scores.confidence = round(0.80 * 100) = 80
adjusted    = 88.65  => scores.adjusted = 89

Inputs and data model

buildA11ySummary({ canonical, domMetrics, textMetrics }) takes three named inputs. Findings are normalized to the shared "canonical findings" shape below before scoring happens, so a report saved before, with findings from another engine, is scored the same way.

1) canonical

Source: this engine's raw output, already normalized into the canonical findings format used throughout the pipeline (not surea11y's raw results).

  • canonical.findings, a flat array of finding objects, one per rule result. Each finding has:
    • outcome: one of "fail", "cantTell", "pass".
    • severity: the engine's own severity string (surea11y's severity, or an alias like "severe"/"medium"/"low"), normalized via impactFromSeverity() into critical/serious/moderate/minor/info/unknown before scoring.
    • occurrences: array of instance matches for this rule (one per matched element).

The code derives its internal violations/incomplete/passes arrays by filtering canonical.findings on outcome, then mapping each finding to { impact: impactFromSeverity(f.severity), nodes: f.occurrences } - so downstream formulas that reference item.impact/item.nodes are reading these derived, not raw, fields. If canonical.findings is missing, all three arrays fall back to empty (defensive; this shouldn't happen on a normal run).

2) domMetrics

Source: collectDomMetrics(page).

  • DOM structural counts and ratios, used for the content-unit density in scores.evidence and for the superseded scores.confidenceByDom/evidenceByDom proxies.

3) textMetrics

Source: collectTextMetrics(page). Accepted either nested under domMetrics.textMetrics (the code checks there first) or as this separate top-level parameter (used if domMetrics.textMetrics isn't present).

  • Text and control heuristics (links, buttons, text density), used as mild confidence signals and as raw outputs for dashboards.

Important: in the code, domTotal is defined as max(1, domMetrics.totalElements) and is used as a normalization base for per-1k computations. This makes the calculations stable even on empty or error pages.

Common helper functions

Clamp

clamp(n, min, max) = max(min, min(n, max))

Saturating score (satScore)

This maps a non-negative value into a 0..100 score with diminishing returns.

satScore(x, s) = 100 * (1 - exp(-max(0, x) / s))
  • x is the input signal, any unit.
  • s is the saturation scale. Smaller s saturates faster.

Impact weights for findings

Each finding has an impact string (normalized from the engine's own severity - see the Glossary). The code assigns weights:

critical = 10
serious  =  6
moderate =  3
minor    =  1
info     =  0.5

If impact doesn't match any of the above (including missing or unknown), the default is 2 - deliberately higher than minor, so an unrecognized severity string never gets weighted as if it were known to be low-impact.

Weighted breadth (sumWeightedRuleBreadth)

“Breadth” counts how many distinct rules fire, weighted by impact. Each rule contributes once, regardless of how many nodes it matches.

sumWeightedRuleBreadth(items) = Σ weightForImpact(item.impact)

Weighted instance depth (sumWeightedInstanceDepth)

“Depth” measures how many nodes rules fire on, weighted by impact, but with a sublinear transform so one rule matching many nodes does not dominate.

n = item.nodes.length (or 0)
sumWeightedInstanceDepth(items) = Σ weightForImpact(item.impact) * sqrt(max(0, n))

DOM metrics

Collected inside the page via a breadth-first traversal, capped by maxNodes (default 20000). If the cap is reached, capped = true.

How “evaluable” and “semantic” are counted

  • Semantic tags: element tag is in the SEMANTIC_TAGS set (main, nav, headings, lists, form elements, table elements, details, dialog, and more).
  • Evaluable tags: element tag is in EVALUABLE_TAGS (interactive and key semantic tags). This is a broader “worth checking” proxy.

Custom control heuristic

An element is counted as a custom control if it is not a native interactive tag and any of these apply:

  • An interactive ARIA role (button, link, checkbox, etc.)
  • A stateful role (dialog, tablist, menu, etc.)
  • An onclick handler paired with a focusability signal - a focusable tabindex, an interactive role, or contenteditable="true"
  • A focusable tabindex, on its own

contenteditable="true" alone does not count - it only contributes as one of the focusability signals that must be paired with an onclick handler. An element with contenteditable="true" and nothing else (no onclick, no tabindex, no interactive role) is not counted as a custom control.

Hidden heuristic

An element counts as hidden if any of the following apply:

  • hidden attribute present
  • aria-hidden="true"
  • Otherwise, only when includeComputedVisibility is true: inline style contains display:none or visibility:hidden (a cheap pre-check), or failing that, the computed style is display:none or visibility:hidden

The inline-style pre-check and the computed-style check are both gated behind includeComputedVisibility - when that option is false, only the hidden attribute and aria-hidden="true" are checked; inline styles are not inspected either.

Text metrics

Collected inside the page, using a traversal that skips hidden containers early. It aims to be language-agnostic and mostly formatting-stable (whitespace collapsed). Output is intended as signals, not pass or fail.

Core counting rules

  • Text length is measured by collapsing whitespace: s.replace(/\s+/g, ' ').trim().length
  • Only direct text node children of visited elements are added to totalVisibleTextChars.
  • To avoid runaway pages, there is a max text cap (maxTextChars, default 2,000,000).

In plain English

This section turns canonical findings into a single “risk” number by combining two ideas: how many different rule types fail (breadth) and how widespread the failures are (depth). Both are weighted by severity, and depth is normalized against how much of the page there was to evaluate. The result is then flipped into an “evidence” score so that higher is better.

Risk and evidence

The summary computes “risk” from canonical findings by combining breadth and depth, then converts it into an “evidence” score. This is what drives scores.evidence and, through it, scores.adjusted.

1) Breadth

violationBreadth  = Σ weightForImpact(v.impact)  for v in violations
incompleteBreadth = Σ weightForImpact(i.impact)  for i in incomplete

2) Content units

Depth is normalized against how much of the page there was to evaluate, not raw DOM size - wrapping a page in a thousand extra <div>s should not make its density look better without a single defect being fixed. The unit falls back through progressively coarser signals so a page still yields a finite density instead of dividing by zero:

unit = evaluable elements, if any
     : else interactive elements (native + custom), if any
     : else visible word count / 100, if any
     : else 1 (no content signal at all)

3) Depth per content unit

violationDepthPerUnit  = ( Σ weightForImpact(v.impact) * sqrt(v.nodes.length) / unitSize ) * 100
incompleteDepthPerUnit = ( Σ weightForImpact(i.impact) * sqrt(i.nodes.length) / unitSize ) * 100

4) Risk

Risk is built from four saturating components and then normalized back to 0..100.

riskContentRaw =
  satScore(violationBreadth, 8)
  + 0.25 * satScore(incompleteBreadth, 10)
  + satScore(violationDepthPerUnit, 35)
  + 0.2 * satScore(incompleteDepthPerUnit, 45)

riskWeightsSum = 1 + 0.25 + 1 + 0.2 = 2.45

riskContent = clamp(riskContentRaw / riskWeightsSum, 0, 100)

5) Evidence

Evidence is simply the inverse of risk.

evidence = clamp(100 - riskContent, 0, 100)

Interpretation: “Evidence” is not a compliance score. It is a signal derived from automated checks, which are incomplete by nature.

Superseded: the DOM-normalized model

An earlier version of this pipeline normalized depth per 1000 raw DOM nodes instead of per content unit. That model is still computed and returned - as inputs.risk.axeRaw/axeClamped and scores.evidenceByDom - purely so a run can be compared against how it used to score. It no longer feeds the headline scores.evidence or scores.adjusted.

violationDepthPer1k  = ( Σ weightForImpact(v.impact) * sqrt(v.nodes.length) / domTotal ) * 1000
incompleteDepthPer1k = ( Σ weightForImpact(i.impact) * sqrt(i.nodes.length) / domTotal ) * 1000

riskAxeRaw = satScore(violationBreadth, 8) + 0.25 * satScore(incompleteBreadth, 10)
           + satScore(violationDepthPer1k, 35) + 0.2 * satScore(incompleteDepthPer1k, 45)
riskAxe = clamp(riskAxeRaw / 2.45, 0, 100)
evidenceByDom = clamp(100 - riskAxe, 0, 100)

Scores

Confidence

In plain English

Confidence is not about how accessible the page is, it is about how much you should trust the automated evidence on that page. It comes from the engines themselves: each finding an engine reports can carry its own confidence, and scores.confidence is the mean of that, over the findings a verdict actually rests on (fail/cantTell). Not every engine reports one, so this can end up unmeasured rather than guessed.

// Only fail/cantTell findings are considered - those are what a verdict rests on.
verdicts = findings where outcome is 'fail' or 'cantTell'
withConfidence = verdicts where a numeric confidence (0..1) was reported

confidence      = mean(withConfidence.confidence)   // null if withConfidence is empty
confidenceCoverage = withConfidence.length / verdicts.length

surea11y maps its own high/medium/low to a confidence, but a finding may carry none (one from a report saved before, with another engine's). Dropping those - rather than defaulting them to some value - keeps the mean from silently describing only a subset of the findings while reading as though it covered everything. confidenceCoverage is what says how much of the evidence confidence actually speaks for.

Reported confidenceSource

confidenceSource =
  'notMeasured' if no verdict carried a confidence
  'engine'      if every verdict did (confidenceCoverage == 1)
  'partial'     otherwise

Effective confidence, used by the headline

Uncertainty is applied only over the evidence it was actually measured on, so a confidence reported for some findings can't speak for the others in either direction:

effectiveConfidence =
  1                                                  if confidence is null (nothing measured)
  1 - (1 - confidence) * clamp(confidenceCoverage, 0, 1)   otherwise

Adjusted accessibility risk ind.

In plain English

The adjusted score is evidence, discounted when automation is less reliable - but the discount is spent out of the headroom above the risk, not multiplied straight onto it. Multiplying overshoots: a risk of 92 at confidence 0.82 used to come to 108, clip at 100, and report a score of exactly 0 - the same 0 a page with double the findings would get. Spending the headroom keeps the same shape (no inflation at zero risk or full confidence, strictly worse with more risk or more uncertainty) without ever needing to clip.

This is the headline index exposed as scores.adjusted, built with riskContent (100 - evidence, see the risk and evidence section above) and effectiveConfidence above:

composeAdjusted(risk, confidenceRatio):
  uncertainty = 1 - confidenceRatio
  inflated = risk + uncertainty * risk * ((100 - risk) / 100)
  return clamp(100 - inflated, 0, 100)

adjusted = composeAdjusted(riskContent, effectiveConfidence)

Superseded: the multiplicative model

An earlier version of this pipeline computed confidence as a penalty chain over DOM complexity signals (starting at 1.0, floored at 0.6) and multiplied it straight onto evidence. Both pieces are still computed and returned - as scores.confidenceByDom and scores.adjustedByDom - purely so a run can be compared against how it used to score. Neither feeds the headline scores.confidence/scores.adjusted, or the flags below, any more.

confidenceByDom = 1.0
if dom.coverageRatio is in interval key 'warn' then confidenceByDom -= 0.06
if dom.hiddenRatio is in interval key 'warn' then confidenceByDom -= 0.05
if dom.statefulComponentsCount is in interval key 'warn' then confidenceByDom -= 0.05
if dom.customControlsRatio is in interval key 'warn' then confidenceByDom -= 0.05
if shadowHostCount > 0 then confidenceByDom -= 0.02
if domMetrics.capped === true then confidenceByDom -= 0.04
if linksPer1k > 180 then confidenceByDom -= 0.02
if buttonsPer1k > 80 then confidenceByDom -= 0.02
if linksPer1k > 60 AND controls.linksNoTextNoNameRate is in interval key 'warn' then confidenceByDom -= 0.03
if buttonsPer1k > 20 AND controls.buttonsNoTextNoNameRate is in interval key 'warn' then confidenceByDom -= 0.04
if buttonsPer1k > 20 AND buttonsNoTextRate > 0.50 then confidenceByDom -= 0.02
confidenceByDom = clamp(confidenceByDom, 0.60, 1.00)

adjustedByDom = clamp(evidenceByDom * confidenceByDom, 0, 100)

Evaluation state

evidence and adjusted are null rather than a misleadingly clean number when there was nothing to score against - an empty denominator should not read as a clean page. scores.evaluationState says why: 'evaluated', 'notEvaluated', 'notMeasurable' (too little of the page carried a content unit to compute a density) or 'unknown' (no coverage summary supplied) - with criteriaEvaluated/criteriaInScope as the denominator to read the state against.

Rounding rules in the output object

The summary returns a mix of raw values (rounded) and scores (rounded). Reproduce the same rounding for identical outputs.

  • scores fields are rounded to integers, or left null when not evaluated/measured:
    • evidence, adjusted, avgPageAccessibility are Math.round(...), or null when evaluationState is not 'evaluated'.
    • confidence is Math.round(confidence * 100) (so 0.85 becomes 85), or null when nothing was measured.
    • confidenceCoverage is Math.round(confidenceCoverage * 100), or null alongside an unmeasured confidence.
    • evidenceByDom, confidenceByDom (as a percentage), adjustedByDom - the superseded model above, always numeric.
  • Many inputs are rounded for display stability:
    • breadth.*, depthPer1k.*, depthPerContentUnit.*, and risk.* are rounded to one decimal.
    • Rates and shares are rounded to three decimals.
    • Per-1k counts are rounded to one decimal.

In plain English

Flags are decision helpers. They answer practical questions like: “Should I schedule manual review for this page?” The boolean itself is narrowed to conditions that genuinely mean a human has to look; DOM and control complexity signals (Shadow DOM, many stateful components, icon-only controls, DOM sampling caps) are reported as reasons alongside it, but no longer decide it on their own - they fire on most real pages, which made the flag permanently true and therefore useless for triage.

Flags

flags.manualReviewNeeded

manualReviewNeeded =
  evaluationState === 'notEvaluated'
  OR hasIncomplete                                  // any cantTell finding
  OR (confidence is not null AND confidence < 75)   // scores.confidence's 'bad' band
  OR domMetrics.capped === true

flags.manualReviewReasons

A human-readable list, built independently of the boolean above - a reason can appear here even when manualReviewNeeded is false, since most of them are complexity signals rather than blockers:

'no criteria were evaluated on this page'                          if evaluationState === 'notEvaluated'
'checks reported results that need human confirmation'             if hasIncomplete
'the engine was not confident about what it found'                 if confidence is not null AND confidence < 75
'only N% of what was found carried a reliability signal, ...'      if confidence was measured but confidenceCoverage < 100%
'too little of the page was testable to measure how dense...'      if evaluationState === 'notMeasurable'
'the scan hit a size cap, so results are partial'                  if domMetrics.capped === true
'many stateful components, whose states automation does not exercise'  if dom.statefulComponentsCount is in 'warn'
'a lot of hidden or conditional content that was not in scope'     if dom.hiddenRatio is in 'warn'
'shadow DOM present, which can hide content from checks'           if shadowHostCount > 0
'icon-only links whose accessible names need checking'             if linksPer1k > 60 AND controls.linksNoTextNoNameRate is in 'warn'
'icon-only buttons whose accessible names need checking'           if buttonsPer1k > 20 AND controls.buttonsNoTextNoNameRate is in 'warn'

Portfolio / multi-page summaries

In plain English

Everything above this section describes a single page. When a run scans several pages, a separate file (global-summary.js) aggregates their individual summaries into one portfolio-level report. It reuses the same score names (scores.evidence, scores.adjusted, etc.) but computes them differently - this section is a scoped overview, not a full formula reference for that file.

How aggregation differs from a single page

  • Peak-like complexity metrics use P90 across pages (depthMax, statefulComponentsCount): the 90th percentile, not the max or the mean. This gives a "robust peak" that isn't inflated just because you scanned more pages, and isn't hidden by averaging.
  • Confidence uses the minimum across pages ("weakest-link reliability"), not a recomputation - if any single page has low confidence, the whole portfolio's confidence reflects that. scores.adjusted is then the same headroom-based composeAdjusted(risk, confidenceRatio) from the single-page section above, fed the portfolio's own evidence and (minimum) confidence: composeAdjusted(100 - evidence, confidence / 100).
  • Other DOM/text totals and ratios are summed across pages and ratios are recomputed from those sums (not averaged per-page), and breadth/depth use the same weighted formulas as a single page, but with rule occurrences grouped per-URL first (Σ_rules weight(impact) * Σ_urls sqrt(occurrencesOnThatUrl)), so a rule firing on many pages doesn't get double-counted the way summing raw occurrences would.
  • scores.avgPageAccessibility is the mean of the scanned pages' own scores.adjusted values (see the headline numbers table above).
  • stats.pageAccessibility is a full distribution object over the per-page scores: n, min, max, mean, median, p10, p25, p75, p90, iqr, stddev - useful for seeing whether a portfolio's score is driven by a few bad pages or is uniform.

Metric definitions and intervals

a11y-metric-defs.cjs provides names, help text, min and max, and interval bands used by your UI and by interval-based logic (isAtOrAboveInterval).

How interval checks work

Given a metric key, a numeric value, and an interval key (for example 'warn'), the check returns true if the value lies inside the interval range (inclusive bounds). Intervals may use to: Infinity.

isAtOrAboveInterval(metricKey, value, intervalKey):
  for each interval in METRIC_DEFS[metricKey].intervals:
    if interval.key !== intervalKey: continue
    if interval.to is Infinity:
      return value >= interval.from
    else:
      return value >= interval.from AND value <= interval.to

Note: This function is used as a generic “band membership” check, not strictly “at or above”. For finite intervals it is a normal inclusive range check.

Reproducibility checklist

  1. Use the same caps and options:
    • collectDomMetrics defaults: maxNodes = 20000, includeComputedVisibility = true.
    • collectTextMetrics defaults: maxNodes = 20000, includeComputedVisibility = true, maxTextChars = 2000000.
  2. Ensure domMetrics.totalElements is available and apply domTotal = max(1, totalElements).
  3. Compute breadth and depth using the exact impact weights and the sqrt(nodes.length) transform.
  4. Pick the content unit in the same fallback order (evaluable, then interactive, then visible words / 100, then 1), and use the exact saturation scales (8, 10, 35, 45) and the same component weights (1, 0.25, 1, 0.2) to get riskContent and evidence.
  5. Compute confidence as the mean of the per-finding confidence the engine(s) reported over fail/cantTell findings, with confidenceCoverage as the share of those that carried one - null/0 when none did.
  6. Derive effectiveConfidence from confidence/confidenceCoverage, then compute adjusted = composeAdjusted(riskContent, effectiveConfidence) (the headroom-based composition, not a multiplication).
  7. Apply the same rounding rules when producing the final JSON used by your UI.

To also reproduce the superseded per-1k-DOM-nodes model (evidenceByDom, confidenceByDom, adjustedByDom): use domTotal instead of a content unit for the depth terms, apply the DOM-complexity confidence penalties in the same order and clamp to [0.60, 1.00], then compute adjustedByDom = clamp(evidenceByDom * confidenceByDom, 0, 100).

Worked example, from raw inputs to scores

This example shows the minimum actions needed to replicate the scores. Use it to validate another implementation. Values below are illustrative, the important part is the order of operations and rounding. 

// 1) Pick the content unit (evaluable, else interactive, else words/100, else 1)
unitSize = max(1, primaryContentUnit(domMetrics, textMetrics).size)

// 2) Compute breadth and depth per content unit
violationBreadth = sumImpactWeights(violations)
incompleteBreadth = sumImpactWeights(incomplete)

violationDepthPerUnit =
  (sum(impactWeight(v) * sqrt(v.nodes.length)) / unitSize) * 100

incompleteDepthPerUnit =
  (sum(impactWeight(i) * sqrt(i.nodes.length)) / unitSize) * 100

// 3) Convert into risk, then evidence
riskContentRaw =
  satScore(violationBreadth, 8)
  + 0.25 * satScore(incompleteBreadth, 10)
  + satScore(violationDepthPerUnit, 35)
  + 0.2  * satScore(incompleteDepthPerUnit, 45)

riskContent = clamp(riskContentRaw / 2.45, 0, 100)
evidence = clamp(100 - riskContent, 0, 100)

// 4) Compute confidence: mean of the per-finding confidence engines reported
//    on fail/cantTell findings, plus how much of the evidence it covers
confidence = mean(findings.confidence where measured)          // null if none did
confidenceCoverage = countMeasured / countVerdicts              // 0 if none did

// 5) Spend uncertainty only over the evidence it was measured on
effectiveConfidence =
  confidence === null ? 1 : 1 - (1 - confidence) * clamp(confidenceCoverage, 0, 1)

// 6) Compute adjusted - headroom-based, not a multiplication
adjusted = composeAdjusted(riskContent, effectiveConfidence)

// 7) Apply output rounding (evidence/adjusted are null instead if evaluationState
//    isn't 'evaluated'; confidence/confidenceCoverage are null if nothing was measured)
scores.evidence = round(evidence)
scores.confidence = confidence === null ? null : round(confidence * 100)
scores.confidenceCoverage = confidence === null ? null : round(confidenceCoverage * 100)
scores.adjusted = round(adjusted)
